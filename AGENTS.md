# AGENTS.md

## What this is

- Supabase Edge Functions repo for backoffice auth. Two functions: `supabase/functions/login/index.ts` and `supabase/functions/register/index.ts`. Both are untouched boilerplate from `supabase functions new` (identical "Hello from Functions!" handlers) — implement real login/register logic in them.
- No git repo, no CI, no tests, no lint (`npm test` is a stub that fails). Typechecking: `npx tsc --noEmit` (configured via root `tsconfig.json`, covers `supabase/functions/**` only).
- Supabase CLI is installed as npm devDependency (`supabase` ^2.115.0); run it via `npx supabase ...` or `./node_modules/.bin/supabase`.

## Deno / deno.json (why it exists)

- Edge Functions execute on the Deno runtime in production — that cannot be avoided. But you do **not** need Deno installed locally:
  - `supabase functions serve` uses the CLI's own Edge Runtime; `supabase functions deploy` bundles the function. Neither requires a local Deno binary.
- Each function's `deno.json` is the **import map** (dependency manifest) auto-generated by the CLI and wired in via `supabase/config.toml` (`import_map = "./functions/login/deno.json"`). Do not delete it. Add function dependencies there as `npm:`/`jsr:` specs (e.g. `"@supabase/server": "npm:@supabase/server@^1"`) — that is the only place function deps are declared; at deploy time the CLI bundles them.
- Root `package.json` devDependencies (`@supabase/server`, `@supabase/functions-js`, `typescript`) exist **only** so `tsc`/the editor language server can resolve imports without installing Deno. Keep their versions in sync with the import maps; they are never used at runtime.
- Quirk: the CLI's `supabase functions new` template imports `@supabase/functions-js/edge-runtime.d.ts`, but that file only ships at `src/edge-runtime.d.ts` in both the npm and jsr packages — the original import fails in TS *and* Deno. Use `@supabase/functions-js/src/edge-runtime.d.ts` (already fixed in both functions).
- Per-function `.npmrc` is only for private npm registries; leave as-is.

## Commands

- `npx supabase start` — local stack (requires Docker); functions then live at `http://127.0.0.1:54321/functions/v1/<name>`, invoked with header `apiKey: sb_publishable_...`
- `npx supabase functions serve <name> --no-verify-jwt` — serve a single function locally
- `npx supabase functions deploy` — deploy all functions
- `npx supabase functions new <name>` — scaffold a function (creates index.ts + deno.json + .npmrc)

## Config

- Both functions have `verify_jwt = false` in `supabase/config.toml`; requests are key-validated via the `apiKey` header.
- Handler pattern: `export default { fetch: withSupabase({ auth: ["publishable", "secret"] }, async (req, ctx) => {...}) }` from `@supabase/server`. `ctx.supabaseAdmin` bypasses RLS — use only for privileged operations.
